# YClaw 后续拓展方向与推进逻辑

> 基于 `docs/prd.md`、`docs/plan.md`、`docs/specs.md`、`docs/specs-enhancements.md`、`docs/plan-automation-browser-ops-v1.md`、`docs/specs-automation-browser-ops-v1.md` 以及现有审查/整改计划整理。

---

## 1. 项目定位再确认

| 维度 | 结论 |
| --- | --- |
| 产品本质 | YClaw 是一个模块化、插件化、可自动化的桌面工作台容器，不是单一浏览器、单一股票工具或单一 AI 聊天工具。 |
| 核心人群 | 数据采集工程师、自动化工程师、量化/数据分析用户、高级插件用户。 |
| 当前主线 | 以“自动化采集产品化”为近期最优主线，把浏览器、任务、调度、结果、日志、AI 辅助串成闭环。 |
| 长期形态 | 桌面端综合生产力平台：自动化/RPA + 数据分析 + AI 助理 + 插件生态 + 模板市场。 |

## 2. 当前阶段判断

| 状态 | 说明 | 推进含义 |
| --- | --- | --- |
| 基础平台已规划清楚 | Electron、Vite MPA、IPC、SQLite、插件、AI、自动化、股票模块均有规格定义。 | 不需要重新设计大架构，应按现有文档收敛执行。 |
| V1.0/V1.1 已有较多“完成”标记 | 文档显示基础模块、增强 UI、AI 基础设施已有实现或部分实现。 | 后续重点不是继续堆新概念，而是核验真实闭环。 |
| 自动化采集已有单独产品化计划 | `plan-automation-browser-ops-v1.md` 已明确一期目标：建任务 → 定时执行 → 查看结果 → 异常介入 → 复跑。 | 这是下一阶段最适合落地的主路线。 |
| 实现缺口计划已经指出风险 | `implementation-gap-remediation` 指出主进程装配、IPC、AI、插件、浏览器模块可能存在半成品状态。 | 在大规模拓展前必须先补齐缺口，否则新功能会建立在不稳定地基上。 |

## 3. 后续拓展总逻辑

YClaw 后续不宜按“功能清单”横向扩张，而应按“用户闭环”纵向打穿。

| 层级 | 目标问题 | 关键能力 | 成功标志 |
| --- | --- | --- | --- |
| L1 可运行 | 用户能不能完成一次任务？ | 任务创建、手动执行、基础步骤运行、状态反馈。 | 一个任务可以从创建到执行完成。 |
| L2 可调度 | 用户能不能把任务交给系统定时跑？ | 调度器、执行队列、并发控制、超时、失败重试。 | 任务能按计划稳定触发并记录批次。 |
| L3 可观察 | 用户能不能知道发生了什么？ | 结果中心、结构化日志、截图、执行步骤时间线。 | 每次执行可查、可筛选、可导出、可定位失败。 |
| L4 可介入 | 失败时用户能不能接管？ | 浏览器介入台、断点恢复、登录态绑定、人工恢复执行。 | 登录失效、验证码、元素变更等场景可人工处理后继续。 |
| L5 可复用 | 用户能不能降低重复配置成本？ | 规则录制、提取模板、模板复制、多站点模板库。 | 常见任务可通过模板快速创建。 |
| L6 可智能 | 系统能不能辅助判断和优化？ | AI 失败诊断、规则草稿、重试策略、任务问答。 | AI 能基于任务、日志、结果给出可执行建议。 |
| L7 可生态 | 能不能沉淀第三方能力？ | 插件化采集、站点适配器、插件市场、社区模板。 | 外部插件/模板能安全安装、运行和复用。 |

## 4. 推荐产品路线

### 4.1 近期主路线：自动化采集产品化

| 阶段 | 目标 | 覆盖模块 | 交付结果 |
| --- | --- | --- | --- |
| Phase 0 | 实现缺口整改 | App 装配、IPC、AI、任务、股票、插件、浏览器、窗口/托盘。 | 文档标记与真实实现对齐，核心通道不再是 UI 壳。 |
| Phase 1 | 任务与调度底座 | 任务中心、批次、调度器、执行队列。 | 任务可创建、启动、暂停、恢复、复跑。 |
| Phase 2 | 结果与日志闭环 | 结果中心、结构化日志、导出、错误聚合。 | 每个批次可追溯结果、日志、截图和失败原因。 |
| Phase 3 | 浏览器介入闭环 | 浏览器介入台、断点恢复、会话绑定。 | 失败现场可观察、可接管、可恢复自动执行。 |
| Phase 4 | 录制与模板效率 | 规则录制器、提取模板、模板复制。 | 用户不再主要依赖手写 JSON 配置任务。 |
| Phase 5 | AI 任务助理 | 任务状态问答、失败解释、规则草稿、重试建议。 | AI 成为自动化工作流的辅助层，而不是孤立聊天窗。 |
| Phase 6 | 插件化与生态 | 站点适配器、结果处理器、采集插件、模板市场。 | 采集能力可扩展、可分发、可复用。 |

### 4.2 暂不作为近期主路线的方向

| 方向 | 暂缓原因 | 适合启动条件 |
| --- | --- | --- |
| 股票分析深度增强 | 当前自动化主链路更能体现产品核心价值。 | 自动化 M5 验收通过，结果/调度/日志稳定。 |
| 插件市场生态 | 需要分发、安全、审核、后端服务和冷启动内容。 | 插件生命周期、本地安装、权限隔离先闭环。 |
| 团队协作与云同步 | 涉及账号、权限、云端后端、同步冲突处理。 | 本地单机产品稳定且有明确团队用户需求。 |
| 大型可视化流程编排 | 复杂度高，容易拖慢核心采集闭环。 | 规则录制和任务模板已经成熟，用户明确需要复杂流程。 |
| AI 主动智能 | 依赖日志、任务、结果、事件流等上下文质量。 | AI 工具调用和任务/日志上下文先稳定。 |

## 5. 模块拓展矩阵

| 模块 | 当前角色 | 下一步重点 | 后续演进 |
| --- | --- | --- | --- |
| App Shell | 应用容器与窗口生命周期基础。 | 核实多窗口/单窗口模型、托盘行为、关闭策略。 | 多实例窗口、模块弹出、多显示器工作流。 |
| IPC / EventBus | 模块间通信地基。 | 补齐缺失 handler，统一错误格式，避免渲染进程永久等待。 | 类型化通道治理、审计、限流、事件回放。 |
| 自动化引擎 | 核心业务引擎。 | 打通任务执行、步骤日志、失败断点、批次状态。 | 条件分支、循环、复杂 RPA 工作流。 |
| 浏览器模块 | 自动化观察台、调试台、接管台。 | 明确真实 `WebContentsView` 接入或短期降级为会话控制台。 | 会话分组、多账号隔离、标签拖拽、站点调试工具。 |
| 结果中心 | 自动化产品可用性的关键。 | 结果列表、详情、筛选、导出、批次关联。 | 异常检测、数据质量评分、结果对比、报表生成。 |
| AI 助手 | 平台智能交互层。 | 先做任务状态、系统状态、失败诊断、导航等低风险工具。 | 操作预览、撤销、主动晨报、调度优化、规则生成。 |
| 插件系统 | 长期生态扩展层。 | 先闭环本地插件扫描、安装、启停、卸载、权限确认。 | 插件沙箱、资源限制、市场、签名、评分。 |
| 股票分析 | 数据分析场景入口。 | 保持基础 K 线和指标能力，避免抢主线资源。 | 策略回测、自定义指标、采集数据联动分析。 |
| 总控页面 | 工作台驾驶舱。 | 展示任务、结果、异常、系统健康和快捷入口。 | 可拖拽布局、小组件、团队看板、模板推荐。 |

## 6. 优先级建议

| 优先级 | 工作项 | 原因 | 不做的代价 |
| --- | --- | --- | --- |
| P0 | 主进程装配与缺失 IPC 注册 | 所有业务模块都依赖主进程 handler。 | UI 看似存在，但关键操作无法真正闭环。 |
| P0 | 任务中心 + 执行队列 | 自动化采集产品的主心骨。 | 产品无法从“演示”进入“日常使用”。 |
| P0 | 结果中心基础版 | 用户必须能看到采集结果和执行历史。 | 即使任务能跑，也无法被验证和复盘。 |
| P0 | 浏览器模块路线决策 | 自动化介入和 WebContentsView 都依赖它。 | 文档、实现和用户预期继续偏离。 |
| P1 | 结构化日志与复跑 | 失败处理是采集类产品的核心体验。 | 任务失败后只能人工排查，使用成本高。 |
| P1 | 会话与登录态管理 | 真实站点采集经常涉及登录态。 | 任务稳定性和复跑能力不足。 |
| P1 | 规则录制与模板 | 降低任务配置门槛。 | 产品仍偏开发者工具，普通用户难上手。 |
| P2 | AI 失败诊断与规则草稿 | 在已有日志/结果基础上增效。 | AI 只能停留在泛聊天，价值不明显。 |
| P2 | 插件化采集能力 | 支持站点适配器和结果处理扩展。 | 长期扩展受限，但不影响一期闭环。 |

## 7. 建议里程碑

| 里程碑 | 周期预估 | 验收口径 |
| --- | --- | --- |
| M0 实现状态校准 | 1 周 | 文档中 `✅ / 🟡 / ⬜` 与代码真实状态一致；核心 IPC 不再缺失。 |
| M1 基础自动化闭环 | 2-3 周 | 任务 CRUD、手动执行、批次记录、基础结果入库可用。 |
| M2 调度与复跑 | 2 周 | 定时任务、并发控制、失败重试、重启恢复、复跑入口可用。 |
| M3 结果与日志中心 | 2 周 | 结果列表/详情/筛选/导出、结构化执行日志、错误聚合可用。 |
| M4 浏览器介入台 | 2-3 周 | 失败现场恢复、人工接管、断点恢复、会话绑定可用。 |
| M5 录制与模板 | 2-3 周 | 交互式录制器、提取模板 CRUD、模板复制可用。 |
| M6 AI 任务助理 | 2 周 | AI 可查询任务状态、解释失败、生成规则草稿、推荐重试策略。 |

## 8. 验收指标

| 指标 | 建议目标 | 验证方式 |
| --- | --- | --- |
| 任务执行成功率 | 3 个基准站点连续 7 天成功率 ≥ 90%。 | 统计批次成功率。 |
| 失败可定位率 | ≥ 90% 失败批次可通过日志 + 截图定位原因。 | 抽样人工复核。 |
| 失败可介入率 | 登录失效、验证码、元素变化三类场景均可接管。 | 场景演练。 |
| 结果可追溯性 | 每条结果可关联任务、批次、规则、日志、截图。 | 数据链路检查。 |
| 重启恢复 | 应用重启后 30 秒内恢复调度。 | kill 进程后重启验证。 |
| 查询性能 | 1 万条结果分页查询 < 500ms。 | 本地压测。 |
| 用户上手 | 新用户 15 分钟内完成首个任务创建和执行。 | 可用性测试。 |

## 9. 决策建议

| 决策点 | 推荐结论 |
| --- | --- |
| 产品主线 | 选择“自动化采集产品化”，暂缓横向生态扩张。 |
| 浏览器模块 | 如果目标是兑现原始 SPEC，优先真实接入 `WebContentsView`；如果目标是快速交付，短期降级为“浏览器会话控制台”并同步文档。 |
| AI 助手 | 不做泛聊天优先，先做任务助理、失败诊断、规则草稿和状态问答。 |
| 插件系统 | 先闭环本地生命周期和权限确认，再考虑插件市场。 |
| 股票分析 | 保持基础能力，待自动化采集稳定后再回归策略回测和指标扩展。 |

## 11. 总结

YClaw 最合理的拓展路径是：

> 先做稳“自动化采集闭环”，再做强“浏览器介入与结果追溯”，随后用“AI 助手”和“插件系统”提高效率与扩展性，最后再进入模板市场、团队协作和生态化阶段。

近期不建议同时发散到股票深度分析、插件市场、团队云同步和大型流程编排。它们都是合理方向，但应排在自动化采集主链路稳定之后。
