# YClaw 本地任务工具台重构设计说明

> 本文是产品级重构设计草案，用于把 YClaw 从“多模块桌面容器”收敛为“本地任务工具台”。  
> 审核通过后，再拆分为可执行 spec 与 implementation plan。

## 1. 背景

当前 YClaw 已经具备 Electron 桌面壳、自动化引擎、内嵌浏览器、Runner 调度、Data Center、AI 助手、插件、MCP、Task-as-Code 等能力。但这些能力目前按技术模块并列展示，用户打开应用后看到的是“股票分析、自动化、浏览器、插件、热点、评论、签到、数据中心”等入口，缺少一个贯穿始终的工作对象。

这导致产品体验出现三个问题：

- 主线不清：用户不知道每天应该围绕什么使用 YClaw。
- 功能空大：模块很多，但每个模块都像能力展示，不像可持续使用的工具。
- 推进发散：后续继续补模块会扩大复杂度，却不一定形成核心卖点。

本次重构的核心判断是：YClaw 不应继续作为“综合生产力平台”推进，而应收敛为一个本地优先的任务工具台。

## 2. 产品定位

YClaw 是一个本地优先的任务工具台，用于把重复的网页操作、采集、监控、签到、评论分析等工作沉淀为可运行、可复盘、可导出的任务资产。

一句话卖点：

> 把重复网页工作做成可运行、可监控、可复盘、可导出的本地任务。

核心价值：

| 价值 | 说明 |
| --- | --- |
| 本地可控 | 账号、浏览器会话、任务数据、结果文件保留在本机，适合不希望上云的个人和小团队。 |
| 任务资产化 | 用户不是运行一次性脚本，而是沉淀任务模板、参数、历史、结果和失败处理记录。 |
| 自动化 + 人工介入 | 任务自动运行，失败时可进入浏览器接管，处理后继续运行或重试。 |
| 结果闭环 | 每次运行都能产出结果、报告、日志、截图或导出文件，避免“跑完就散”。 |

## 3. 目标用户与典型场景

### 3.1 目标用户

第一阶段不面向泛办公用户，而面向需要重复处理网页任务的个人和小团队：

- 运营人员：需要每天执行签到、监控、评论处理、数据归档。
- 数据采集人员：需要定期采集网页数据并导出。
- 自动化配置人员：需要把手工网页流程沉淀成可复用任务。
- 小团队负责人：需要知道任务是否运行、哪里失败、产出了什么。

### 3.2 典型场景

| 场景 | 用户目标 | YClaw 应提供的闭环 |
| --- | --- | --- |
| 京东签到 | 每天自动执行签到并记录结果 | 创建签到任务 -> 定时运行 -> 记录成功/失败 -> 查看历史 |
| 热点监控 | 定期抓取热点源并生成报告 | 选择热点模板 -> 配置来源 -> 运行采集 -> 生成报告 -> 导出 |
| 评论监控 | 采集评论并生成回复建议 | 配置评论源 -> 运行采集 -> AI 生成建议 -> 复核 -> 输出报告 |
| 电商价格监控 | 定期检查页面价格变化 | 录制浏览器步骤 -> 提取字段 -> 定时运行 -> 失败介入 -> 导出结果 |

## 4. 重构范围

### 4.1 需要做什么

本次重构重点是产品壳、信息架构和任务闭环，不是从零重写底层能力。

需要完成：

- 重构一级菜单，改为围绕任务生命周期组织。
- 重做首页，使其成为任务台，而不是模块展示页。
- 将现有签到、热点、评论等功能包装为任务模板。
- 将浏览器、插件、MCP、AI、Runner 等能力收敛到任务创建和运行过程中。
- 将 Data Center 重命名和改造为结果库，围绕任务结果组织。
- 建立统一的任务生命周期、状态、操作和验收口径。

### 4.2 暂不做什么

第一阶段不做：

- 完整股票投研终端。
- 插件市场和插件生态扩张。
- 云端多租户、团队权限、账号体系。
- 大屏式 KPI 仪表盘。
- 通用 AI 聊天机器人。
- 底层数据库和服务的大面积重写。

## 5. 信息架构设计

### 5.1 新一级菜单

建议将一级菜单收敛为 5 个：

| 菜单 | 作用 | 承接现有能力 |
| --- | --- | --- |
| 任务台 | 今日任务、正在运行、失败待处理、最近结果、快速创建 | 原总览、自动化状态、签到状态、热点/评论运行概览 |
| 任务编辑器 | 创建任务、选择模板、配置参数、录制步骤、设置定时 | 自动化编辑、浏览器录制、Task-as-Code、模板 |
| 运行监控 | 批次、日志、截图、失败步骤、人工介入、重试/取消/继续 | 自动化运行、Runner、调度、浏览器介入 |
| 结果库 | 任务产物、数据集、导出、Webhook、质量评分 | Data Center、报告、导出、质量洞察 |
| 能力中心 | 插件、MCP、AI 工具、Runner、浏览器能力、数据源 | 插件中心、MCP、AI、Runner 配置、数据源 |

### 5.2 原菜单处理

| 原一级菜单 | 新处理方式 |
| --- | --- |
| 总览 | 重做为任务台 |
| 自动化 | 拆入任务编辑器和运行监控 |
| 自动签到 | 降级为任务模板 |
| 热点监控 | 降级为任务模板 |
| 评论监控 | 降级为任务模板 |
| 浏览器 | 降级为任务编辑和人工介入工具 |
| 数据中心 | 重命名为结果库 |
| 插件 | 合并到能力中心 |
| 股票分析 | 第一阶段移出主菜单，保留为实验能力或后续专项 |
| 设置 | 可保留在右上角或能力中心内，不作为核心业务入口 |

## 6. 页面设计

### 6.1 任务台

任务台是用户打开应用后的第一屏。它不展示虚假 KPI，不展示模块卡片，而展示真实任务状态。

首屏结构：

```text
------------------------------------------------------+
| 今日任务概览        [新建任务] [从模板创建]          |
+------------------------------------------------------+
| 正在运行                    | 失败待处理             |
| - 任务 A  运行中  3/8       | - 任务 C 登录失效       |
| - 任务 B  排队中            | - 任务 D 选择器失败     |
+------------------------------------------------------+
| 最近完成                    | 最近结果               |
| - 京东签到 成功             | - 热点报告 10:30       |
| - 评论监控 完成             | - 评论建议 09:50       |
+------------------------------------------------------+
| 推荐模板：京东签到 / 热点监控 / 评论监控 / 网页采集 |
+------------------------------------------------------+
```

关键要求：

- 空状态必须引导用户创建第一个任务。
- 所有主按钮都指向任务动作。
- 不展示没有数据来源的“今日执行 28 个工作流”这类假数据。
- 失败任务必须能进入处理动作。

### 6.2 任务编辑器

任务编辑器用于创建和维护任务。

布局：

```text
左侧：任务模板 / 任务类型
中间：任务配置表单
右侧：运行预览 / 参数说明 / 风险提示
底部：保存草稿 / 立即运行 / 启用定时
```

第一版支持：

- 从模板创建任务。
- 编辑任务名称、描述、参数。
- 配置运行方式：手动、定时、一次性。
- 选择 Runner 或使用默认本地 Runner。
- 对网页任务提供浏览器录制入口。
- 保存草稿、启用任务、立即运行。

### 6.3 运行监控

运行监控用于查看任务执行过程，并处理失败。

布局：

```text
顶部：任务批次状态、开始时间、耗时、Runner
左侧：步骤时间线
中间：日志、截图、浏览器介入区域
右侧：失败原因、推荐操作、重试/取消/继续
```

关键要求：

- 用户能看到任务跑到哪一步。
- 失败项必须显示明确原因。
- 需要人工介入时，从这里打开浏览器接管。
- 处理后支持继续运行或重试。

### 6.4 结果库

结果库承接任务运行后的所有产物。

布局：

```text
顶部：任务、状态、时间、类型筛选
中间：结果列表
右侧：结果详情、导出、质量评分、关联运行记录
```

结果类型：

- 结构化数据。
- 报告。
- 日志。
- 截图。
- 导出文件。
- AI 生成建议。

关键要求：

- 每次任务运行后都能找到结果记录。
- 结果必须关联任务和运行批次。
- 支持 CSV/JSON 导出。
- 导出失败、空结果、质量异常必须有明确状态。

### 6.5 能力中心

能力中心不是主工作流，而是任务可调用能力的管理区。

包括：

- Runner 管理。
- 浏览器能力。
- 插件。
- MCP 工具。
- AI Provider。
- 数据源。
- 全局设置。

关键原则：

- 能力中心不应成为用户每天主要停留页面。
- 所有能力最终都要能被任务编辑器或运行监控调用。

## 7. 任务生命周期

统一任务生命周期：

```text
选择模板/新建任务
  -> 配置参数
  -> 保存草稿
  -> 启用任务
  -> 创建运行批次
  -> 执行步骤
  -> 成功 / 失败 / 需人工介入
  -> 产出结果
  -> 复盘 / 导出 / 复用
```

任务状态建议：

第一阶段复用现有 `TaskStatus` 合约，不新增数据库状态值。产品层可以把这些状态翻译成更易懂的中文标签，但 IPC、持久化和筛选条件仍使用现有枚举。

| 状态 | 说明 |
| --- | --- |
| idle | 空闲，未运行 |
| running | 正在运行 |
| paused | 已暂停 |
| completed | 最近一次运行成功 |
| failed | 最近一次运行失败 |

运行批次状态建议：

第一阶段复用现有 `TaskBatchStatus` 合约，不引入 `succeeded`、`paused_for_intervention` 等新状态。界面可显示“成功完成”“等待人工介入”等中文文案，但底层值必须保持兼容。

| 状态 | 说明 |
| --- | --- |
| pending | 等待开始 |
| running | 运行中 |
| success | 成功完成 |
| failed | 失败结束 |
| cancelled | 用户取消 |
| paused | 已暂停 |
| intervention | 暂停等待人工介入 |

产品文案映射建议：

| 底层状态 | UI 文案 |
| --- | --- |
| completed | 成功 |
| success | 成功 |
| failed | 失败 |
| paused | 已暂停 |
| intervention | 需人工介入 |
| pending | 等待中 |
| running | 运行中 |
| cancelled | 已取消 |

## 8. 数据模型建议

第一阶段可以优先复用现有任务、批次、结果、模板、Runner、Data Center 模型，不急于大规模重建数据库。但产品层需要统一这些核心对象。

| 对象 | 说明 |
| --- | --- |
| TaskTemplate | 任务模板，如京东签到、热点监控、评论监控、网页采集 |
| Task | 用户创建的任务实例 |
| TaskRun | 一次任务运行批次 |
| TaskStepRun | 单个步骤运行记录 |
| TaskArtifact | 截图、日志、报告、导出文件 |
| TaskResult | 结构化结果数据 |
| Capability | 浏览器、AI、MCP、插件、Runner、数据源等能力 |

关系：

```text
TaskTemplate -> Task -> TaskRun -> TaskStepRun
                          |
                          +-> TaskResult
                          +-> TaskArtifact
```

## 9. 第一批任务模板

第一阶段至少提供 3 个模板，用来验证真实闭环。

| 模板 | 目标 | 验证闭环 |
| --- | --- | --- |
| 京东签到任务 | 每天执行签到并记录历史 | 配置 -> 运行 -> 成功/失败 -> 历史结果 |
| 热点监控任务 | 采集热点源并生成报告 | 来源配置 -> 采集 -> 报告 -> 导出 |
| 评论监控任务 | 采集评论并生成回复建议 | 评论源 -> 采集 -> AI 建议 -> 结果归档 |

后续可扩展模板：

- 电商价格监控。
- 网页表单批量填写。
- 内容发布前检查。
- 指定页面字段采集。

## 10. AI 设计

AI 助手不再作为通用聊天产品推进，而作为任务辅助能力。

第一阶段 AI 只做：

- 解释失败原因。
- 根据日志和截图生成处理建议。
- 帮用户创建任务草稿。
- 为评论监控生成回复建议。
- 为任务运行结果生成复盘摘要。

AI 不做：

- 无上下文闲聊。
- 替用户直接执行高风险操作。
- 脱离任务生命周期的通用问答。

## 11. 实施方案

### 阶段一：产品壳重构

目标：先重组信息架构，不破坏底层能力。

工作：

- 将一级菜单改为任务台、任务编辑器、运行监控、结果库、能力中心。
- 保留旧路由，但从一级菜单隐藏。
- 将首页重做为任务台。
- 将签到、热点、评论包装为任务模板入口。

验收：

- 打开应用后，首屏展示任务状态和创建入口。
- 一级菜单不再出现股票、浏览器、插件、热点、评论、签到。
- 用户可以从任务台进入任务创建流程。

### 阶段二：任务编辑器最小版

目标：让用户能基于模板创建任务。

工作：

- 实现模板选择。
- 实现任务基础配置表单。
- 支持保存草稿、启用任务、立即运行。
- 支持从任务台进入编辑器。

验收：

- 用户能基于京东签到模板创建任务。
- 用户能基于热点监控模板创建任务。
- 创建后的任务能出现在任务台。
- 任务配置可再次编辑。

### 阶段三：运行监控最小版

目标：让任务运行过程可观察、可处理。

工作：

- 展示任务运行批次。
- 展示步骤、日志、运行状态。
- 支持失败详情。
- 支持重试、取消。
- 接入浏览器人工介入入口。

验收：

- 运行任务时能看到步骤进度。
- 失败任务能进入详情页。
- 至少一种失败场景可以触发人工介入。
- 人工处理后可以继续或重试。

### 阶段四：结果库任务化

目标：让结果围绕任务聚合。

工作：

- 按任务展示结果。
- 展示运行批次关联结果。
- 支持结果详情和导出。
- 保留 Webhook、Token、质量评分能力，但改为任务结果上下文。

验收：

- 每次任务运行后能看到结果记录。
- 用户能导出任务结果。
- 用户能查看历史运行结果。
- 失败、空结果、导出失败都有明确状态。

## 12. 验收标准

### 12.1 产品验收

- 用户能在 3 分钟内创建并运行第一个任务。
- 用户能清楚知道今天哪些任务成功、失败、待处理。
- 用户能从失败任务进入处理动作。
- 用户能找到任务结果并导出。
- 用户不需要理解“模块系统”也能使用产品。

### 12.2 功能验收

- 至少 3 个任务模板可用于创建任务。
- 至少 1 个任务模板能跑完整闭环。
- 至少 1 个失败场景支持重试或人工介入。
- 任务结果能进入结果库。
- 任务、运行批次、结果之间有关联关系。

### 12.3 工程验收

- 原有底层服务不被大面积破坏。
- 新菜单和旧路由兼容。
- 核心页面有组件测试或集成测试。
- `npm run typecheck` 通过。
- `npm run lint` 无新增 error。
- 相关单测通过。

### 12.4 UI 验收

- 首屏不再是模块展示页。
- 所有主按钮都指向任务动作。
- 空状态能引导创建任务。
- 没有不可解释的假 KPI。
- 任务状态颜色、标签、操作一致。
- 页面风格偏工具化，信息密度适中，可快速扫描。

## 13. 风险与取舍

| 风险 | 说明 | 处理方式 |
| --- | --- | --- |
| 重构范围过大 | 如果同时改菜单、模型、服务、页面，容易失控 | 第一阶段只改产品壳和入口组织 |
| 旧模块割裂 | 原模块仍可能保留旧体验 | 旧路由隐藏，逐步迁移到任务生命周期 |
| 模板只是包装 | 如果模板不能真实运行，会继续显得空 | 第一批模板必须至少有一个跑通完整闭环 |
| AI 继续发散 | 通用聊天会稀释主线 | AI 只围绕任务创建、失败处理、结果复盘 |
| 股票模块定位不清 | 股票分析与任务工具台主线弱相关 | 第一阶段移出主菜单，后续单独评估 |

## 14. 成功标准

这次重构成功的标准不是菜单更漂亮，而是用户打开 YClaw 后能立刻回答四个问题：

- 我今天要运行什么任务？
- 现在什么任务正在运行？
- 什么任务失败了，需要我处理？
- 任务产出了什么结果？

当这四个问题能在首屏和主流程中被清楚回答，YClaw 才从“空大的平台”变成“可持续使用的工具台”。
