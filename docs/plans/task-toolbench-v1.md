# YClaw 本地任务工具台 V1 任务拆解

> 来源设计：`docs/design/task-toolbench-redesign.md`  
> 目标：把“本地任务工具台”重构拆成可执行、可验收、逻辑闭环的任务包。  
> 原则：第一阶段复用现有任务、批次、结果、Runner、Data Center、浏览器、AI、插件和 MCP 能力，不做底层大重写。

## 1. 总目标

YClaw V1 重构后，用户打开应用后应能完成一个完整闭环：

```text
选择任务模板
  -> 创建任务
  -> 配置参数
  -> 运行任务
  -> 查看运行过程
  -> 处理失败或人工介入
  -> 查看结果
  -> 导出或复用
```

成功标准不是“菜单更像工具台”，而是用户能在一个连续流程里完成任务创建、运行、监控、结果查看和复盘。

## 2. 范围边界

### 2.1 本次必须完成

- 一级菜单重构为任务台、任务编辑器、运行监控、结果库、能力中心。
- 首页重做为任务台，展示真实任务状态和创建入口。
- 京东签到、热点监控、评论监控包装为任务模板。
- 至少一个模板跑通完整任务闭环。
- 运行监控能展示批次、状态、日志/步骤、失败详情。
- 结果库能按任务聚合结果，并支持查看和导出。
- AI 助手从通用聊天降级为任务辅助入口。

### 2.2 本次不做

- 不重写数据库模型。
- 不新增不兼容的 `TaskStatus` / `TaskBatchStatus`。
- 不做股票投研主线。
- 不做插件市场。
- 不做云端多租户。
- 不做通用 AI 聊天产品。
- 不做大屏式运营仪表盘。

## 3. 状态与兼容约束

第一阶段必须复用现有共享类型和持久化状态。

任务状态使用现有 `TaskStatus`：

| 状态 | UI 文案 | 用途 |
| --- | --- | --- |
| idle | 空闲 | 可运行但当前未执行 |
| running | 运行中 | 当前任务正在执行 |
| paused | 已暂停 | 用户或系统暂停 |
| completed | 成功 | 最近一次运行完成 |
| failed | 失败 | 最近一次运行失败 |

批次状态使用现有 `TaskBatchStatus`：

| 状态 | UI 文案 | 用途 |
| --- | --- | --- |
| pending | 等待中 | 批次已创建但未开始 |
| running | 运行中 | 批次正在执行 |
| success | 成功 | 批次完成且成功 |
| failed | 失败 | 批次失败结束 |
| cancelled | 已取消 | 用户取消 |
| paused | 已暂停 | 批次暂停 |
| intervention | 需人工介入 | 批次等待人工接管 |

实现中不得引入 `succeeded`、`paused_for_intervention`、`needs_intervention` 作为自动化批次状态。签到等专项已有 `needs_intervention` 的场景可在模板适配层映射到任务工具台 UI 文案，但不能污染自动化批次合约。

### 3.1 路由边界

新页面使用新的产品语义路由，旧模块路由保留为兼容入口和内部能力入口。

| 新入口 | 建议路由 | 页面职责 | 旧路由处理 |
| --- | --- | --- | --- |
| 任务台 | `/` 或 `/taskbench` | 聚合任务状态、失败项、最近结果、模板入口 | 原总览内容替换，不保留旧模块卡片 |
| 任务编辑器 | `/tasks/editor` | 模板选择、任务配置、保存、立即运行 | 原自动化编辑能力作为内部能力复用 |
| 运行监控 | `/runs` | 批次列表、运行详情、失败处理、人工介入 | 原自动化运行、浏览器介入内部复用 |
| 结果库 | `/results` | 任务结果、报告、导出、质量状态 | `/data-center` 保留兼容，可重定向或作为内部详情入口 |
| 能力中心 | `/capabilities` | 插件、MCP、AI、Runner、数据源、设置 | `/plugin-center`、`/settings` 保留兼容 |

路由迁移规则：

- 一级菜单只出现新入口。
- 旧路由不删除，避免破坏窗口导航、命令面板、测试和历史链接。
- 旧路由如果仍展示独立模块，必须在页面头部提供返回任务工具台的入口。
- 主进程 `APP_NAVIGATE` 事件优先映射到新入口；旧模块名只作为兼容映射。

### 3.2 数据投影边界

任务台和运行监控第一阶段不新增后端聚合服务，优先在渲染层通过现有 IPC/API 组合出页面 view model。只有当组合逻辑开始重复或性能不可接受时，再下沉为主进程聚合服务。

| 页面 | 所需数据 | 优先复用来源 | 空/缺失处理 |
| --- | --- | --- | --- |
| 任务台 | 任务列表、最近批次、失败项、最近结果 | `TASK_LIST`、`TASK_BATCH_LIST`、`RESULT_LIST`、签到/热点/评论专项状态接口 | 没有数据时展示创建任务空状态 |
| 任务编辑器 | 模板目录、任务详情、能力状态 | 前端模板目录、`TASK_GET`/`TASK_DETAIL`、Runner/MCP/AI/插件状态接口 | 能力缺失时显示风险提示，但允许保存草稿 |
| 运行监控 | 批次列表、批次详情、步骤、错误、截图 | `TASK_BATCH_LIST`、`TASK_BATCH_DETAIL`、`BATCH_RETRY`、介入 IPC | 没有截图或日志时显示“未采集”，不阻断失败处理 |
| 结果库 | 结构化结果、报告、导出任务、质量状态 | `RESULT_LIST`、`RESULT_DETAIL`、`RESULT_EXPORT`、Data Center API、热点/评论报告接口 | 结果为空时显示空结果状态，不伪造数据 |
| 能力中心 | Runner、插件、MCP、AI、数据源状态 | 现有设置页、插件中心、Runner Scheduler、MCP、AI Provider 状态 | 未配置能力显示“未就绪”和配置入口 |

### 3.3 模板适配边界

模板不是新的数据库实体。V1 中模板优先作为前端和适配层的产品配置，用来把现有能力包装为统一创建流程。

模板适配必须满足：

- 模板可以创建或定位一个现有 `TaskFlow`。
- 模板可以声明参数表单，但参数必须能落到现有任务配置、专项 source 配置或运行 payload。
- 模板可以声明能力依赖，但不能强制能力中心先完整上线。
- 模板可以有专项结果来源，例如签到运行历史、热点报告、评论报告。
- 模板不能新增不兼容的任务或批次状态。

模板适配类型：

| 模板 | 适配方式 | 结果来源 | 备注 |
| --- | --- | --- | --- |
| 京东签到 | 创建 `kind = jd-signin` 的 `TaskFlow`，复用现有签到服务 | 签到运行历史，可投影到结果库 | 最小闭环优先选它 |
| 热点监控 | 复用热点 source 和 task compiler，必要时绑定到任务 | 热点报告、热点运行投影 | 不强制迁移旧热点页面 |
| 评论监控 | 复用评论 source、MediaCrawler 导入和 AI 回复服务 | 评论报告、AI 回复建议 | AI 不可用时仍保留采集结果 |

### 3.4 结果归档边界

结果库的目标是“按任务查看产物”，不是第一阶段把所有专项数据强行迁移到同一张结果表。

V1 允许两种结果来源并存：

- 标准结果：现有 `ResultRepository` / Data Center 结果。
- 专项结果：签到运行历史、热点报告、评论报告等专项 repository。

结果库页面需要提供统一展示模型：

| 字段 | 说明 |
| --- | --- |
| resultId | 结果或报告 ID |
| taskId | 关联任务 ID；无法直接关联时需要通过模板/source 建立映射 |
| batchId | 关联批次 ID；专项结果没有批次时显示“未绑定批次” |
| sourceType | `standard`、`signin`、`hot`、`comment` |
| title | 结果标题 |
| status | 结果状态或报告状态 |
| createdAt | 创建时间 |
| exportable | 是否支持导出 |

边界要求：

- 结果库可以聚合多个来源，但不能隐藏来源差异。
- 无法关联 `batchId` 的专项结果不能假造批次 ID。
- 导出失败必须保留导出任务状态和错误信息。
- 后续如需统一写入 `TaskResult`，必须单独设计迁移方案。

### 3.5 草稿与启用边界

设计中的“保存草稿”“启用任务”不是新增 `TaskStatus`。

V1 处理方式：

- 草稿：任务配置未完整时，只保存在任务编辑器本地状态或持久化为 `enabled = false` 的任务。
- 启用：使用现有 `TaskFlow.enabled` 或等价字段表示。
- 运行状态：仍使用现有 `TaskStatus`。
- 定时配置：仍使用现有 `schedule` 配置；是否启用定时由任务启用状态和 schedule 共同决定。

验收时必须区分：

- “任务是否启用”是配置状态。
- “任务是否运行成功/失败”是运行状态。
- “批次是否成功/失败/介入”是批次状态。

## 4. 关键闭环用例

闭环判定标准：

- 有入口：用户知道从哪里开始。
- 有对象：流程必须围绕一个具体任务、批次或结果。
- 有状态：每一步都有明确状态，不依赖口头说明。
- 有动作：用户能继续推进、重试、介入、导出或返回。
- 有产物：运行结束后必须留下结果、日志、报告、截图或失败记录。
- 有回路：用户能从结果或失败回到任务，完成复用或修复。

### UC-01：空状态创建第一个任务

目标用户：第一次打开应用的运营人员。

前置条件：

- 本地没有可展示的任务，或任务台聚合结果为空。

主流程：

1. 用户打开应用，进入任务台。
2. 页面显示空状态，不显示假 KPI。
3. 用户点击“从模板创建”。
4. 用户选择“京东签到任务”模板。
5. 用户填写任务名称和必要参数。
6. 用户保存并立即运行。
7. 系统创建任务和运行批次。
8. 用户跳转到运行监控查看状态。
9. 运行结束后，用户在结果库看到本次结果。

验收：

- 空状态能引导创建任务。
- 用户不用理解旧模块名也能完成创建。
- 任务台、运行监控、结果库之间能互相跳转。
- 不出现股票、插件、浏览器等旧一级菜单干扰主流程。

异常分支：

- 如果模板目录加载失败，空状态展示“模板加载失败”和重试按钮。
- 如果用户只保存草稿，不立即运行，任务台展示该任务为“空闲/未运行”，不进入运行监控。
- 如果创建任务失败，保留表单输入并展示错误原因。

### UC-02：京东签到任务完整成功闭环

目标用户：希望每天自动签到的个人用户。

前置条件：

- 已配置京东签到需要的本地能力。
- 签到模板可用。

主流程：

1. 用户从任务编辑器选择“京东签到任务”。
2. 用户设置任务名称、运行方式和通知偏好。
3. 用户点击“立即运行”。
4. 系统创建 `TaskRun` / 批次。
5. 运行监控显示批次状态为 `running`。
6. 运行成功后，批次状态变为 `success`，任务状态变为 `completed`。
7. 结果库显示签到结果、运行时间和策略信息。
8. 用户可查看历史运行记录。

验收：

- 至少一次运行可从创建到结果完整走通。
- 状态值符合现有 `TaskStatus` / `TaskBatchStatus`。
- 结果记录能关联任务和批次。
- 历史记录能按任务查看。

异常分支：

- 如果登录态缺失，运行监控展示能力或登录缺失提示，并提供登录采集或人工处理入口。
- 如果签到专项返回 `needs_intervention`，任务工具台 UI 显示“需人工介入”，但不把自动化批次状态改成 `needs_intervention`。
- 如果签到成功但没有标准结果记录，结果库从签到运行历史展示专项结果，来源标记为 `signin`。

### UC-03：热点监控任务产出报告

目标用户：需要定期查看热点趋势的运营人员。

前置条件：

- 已有热点源配置能力。
- 热点报告生成能力可用。

主流程：

1. 用户选择“热点监控任务”模板。
2. 用户选择热点来源和采集频率。
3. 用户运行任务。
4. 运行监控展示采集进度。
5. 任务完成后，结果库出现热点报告。
6. 用户打开结果详情。
7. 用户导出报告。

验收：

- 热点任务能创建、运行、生成报告。
- 报告能从结果库打开。
- 导出成功后能看到导出状态。
- 导出失败时有明确错误状态。

异常分支：

- 如果未配置热点来源，任务编辑器允许保存草稿，但立即运行前必须提示补齐来源。
- 如果采集成功但报告生成失败，运行监控显示采集完成，结果库显示报告失败状态。
- 如果报告不支持某种导出格式，导出按钮禁用并说明原因。

### UC-04：评论监控任务生成 AI 回复建议

目标用户：需要处理评论和回复建议的运营人员。

前置条件：

- 评论源配置能力可用。
- AI Provider 未配置时也要有明确提示。

主流程：

1. 用户选择“评论监控任务”模板。
2. 用户配置评论来源。
3. 用户选择是否启用 AI 回复建议。
4. 用户运行任务。
5. 系统采集评论。
6. AI 可用时生成回复建议；AI 不可用时结果中标记“未生成 AI 建议”。
7. 结果库展示评论、建议和报告。

验收：

- AI 可用和不可用两种场景都有明确结果。
- AI 不可用不应导致整个任务结果不可查看。
- 回复建议必须关联评论和任务运行批次。

异常分支：

- 如果 AI Provider 未配置，任务仍可采集评论，结果库显示“未生成 AI 建议”。
- 如果评论采集失败，运行监控展示失败来源和日志。
- 如果 AI 生成失败，评论原始结果仍进入结果库，AI 建议区域显示失败原因。

### UC-05：失败任务处理与重试

目标用户：执行值班员。

前置条件：

- 存在失败批次，状态为 `failed` 或 `intervention`。

主流程：

1. 用户在任务台看到失败待处理任务。
2. 用户点击失败项进入运行监控。
3. 运行监控显示失败步骤、错误信息、最近日志和截图。
4. 如果是 `failed`，用户可点击“重试”。
5. 如果是 `intervention`，用户可点击“人工介入”打开浏览器接管。
6. 用户处理后点击“继续运行”或“重试”。
7. 系统创建新批次或恢复当前批次。
8. 结果库保留失败记录和后续成功记录。

验收：

- 失败原因不能只显示“未知错误”。
- 重试和人工介入入口清晰。
- 失败记录不被成功记录覆盖。
- 任务台失败数量随处理结果更新。

异常分支：

- 如果失败批次没有截图，运行监控显示“未采集截图”，不隐藏错误详情。
- 如果重试创建新批次失败，原失败批次保持不变，并展示重试错误。
- 如果浏览器介入能力不可用，显示能力缺失提示和返回任务台入口。

### UC-06：结果查看与导出

目标用户：数据采集人员或运营负责人。

前置条件：

- 至少存在一个成功运行批次和结果。

主流程：

1. 用户进入结果库。
2. 用户按任务、状态、时间筛选结果。
3. 用户打开结果详情。
4. 用户查看关联任务、运行批次、原始结果和质量状态。
5. 用户选择 CSV 或 JSON 导出。
6. 系统创建导出任务。
7. 导出完成后，用户看到导出路径或状态。

验收：

- 结果必须能追溯到任务和批次。
- 导出入口可用。
- 空结果、导出失败、质量异常都有状态。
- 结果库不再是孤立数据中心，而是任务结果中心。

异常分支：

- 如果结果没有 `batchId`，详情显示“未绑定批次”，但仍允许查看结果。
- 如果结果为空，结果库显示空结果状态，不删除记录。
- 如果导出失败，保留导出任务和错误信息，允许用户重试。

## 5. 任务包拆解

### P0-01：导航与路由收敛

目标：把产品主入口从技术模块切换为任务生命周期。

工作：

- 将一级菜单改为：任务台、任务编辑器、运行监控、结果库、能力中心。
- 保留旧路由用于兼容和内部跳转。
- 旧模块不再作为一级菜单展示。
- 命令面板同步更新新入口。
- 标题栏和模块跳转事件使用新路由映射。

涉及区域：

- `src/renderer/shared/components/AdminPageLayout.tsx`
- `src/renderer/entries/workbench/App.tsx`
- `src/renderer/shared/components/CommandPalette/CommandPalette.tsx`

验收：

- 一级菜单只展示 5 个主入口。
- 旧路由仍能直接访问。
- 从主进程导航事件能进入对应新页面。
- 命令面板不再优先展示旧模块入口。

测试建议：

- 组件测试验证菜单项。
- 路由测试验证旧路由兼容。
- 命令面板测试验证新入口。

### P0-02：任务台首页

目标：把首页从模块展示页改成真实任务状态台。

输入：

- 任务列表。
- 每个任务的最近批次。
- 最近结果或专项报告。
- 模板目录。

输出：

- 任务台 view model：今日概览、运行中、失败待处理、最近完成、最近结果、推荐模板。
- 跳转参数：任务 ID、批次 ID、结果 ID、模板 ID。

工作：

- 删除或隐藏首页假 KPI 和模块卡片。
- 聚合待运行、运行中、失败待处理、最近完成、最近结果。
- 没有数据时显示创建任务空状态。
- 提供“新建任务”“从模板创建”入口。
- 提供失败项进入运行监控的入口。
- 提供最近结果进入结果库的入口。

涉及区域：

- `src/renderer/entries/workbench/pages/Home.tsx`
- `src/renderer/entries/workbench/styles.css`
- 现有任务、批次、结果 IPC/API 封装

边界条件：

- 任务列表加载失败时，显示错误状态和刷新按钮，不显示假数据。
- 批次缺失时，任务仍可展示为“未运行”。
- 结果缺失时，最近结果区域显示空状态。
- 同一任务有多个失败批次时，任务台只展示最新待处理失败，并在运行监控中展示完整历史。

验收：

- 首屏展示任务，而不是模块。
- 无数据时不显示假数据。
- 失败任务可跳转运行监控。
- 最近结果可跳转结果库。

测试建议：

- 空状态组件测试。
- 有任务数据时的任务分组测试。
- 跳转行为测试。

### P0-03：任务模板目录

目标：把签到、热点、评论包装为统一任务模板。

输入：

- 内置模板定义。
- 能力状态。
- 旧模块和服务适配关系。

输出：

- 可复用模板目录。
- 模板参数字段定义。
- 模板能力需求说明。

工作：

- 建立前端模板目录数据结构。
- 模板包含 id、名称、说明、参数 schema、能力需求、默认运行方式。
- 内置 3 个模板：京东签到、热点监控、评论监控。
- 模板入口从任务台和任务编辑器复用。
- 明确模板和旧模块路由/服务的适配关系。

建议模板字段：

| 字段 | 说明 |
| --- | --- |
| id | 模板唯一标识 |
| name | 模板名称 |
| description | 模板说明 |
| category | 模板分类 |
| requiredCapabilities | 所需能力 |
| parameterFields | 参数表单字段 |
| defaultSchedule | 默认运行方式 |
| adapter | 对应现有服务或路由 |

边界条件：

- 模板目录可以先前端静态定义，不要求后端存储模板。
- 能力缺失不隐藏模板，只显示“需要配置”的提示。
- 模板参数字段必须能映射到现有任务配置或专项配置，不能出现无处落库的字段。

验收：

- 三个模板都能在任务台和任务编辑器看到。
- 用户能从模板进入配置页。
- 模板显示所需能力和风险提示。

测试建议：

- 模板目录单测。
- 模板卡片组件测试。

### P0-04：任务编辑器最小闭环

目标：让用户能基于模板创建任务。

输入：

- 模板 ID。
- 任务名称。
- 模板参数。
- 运行方式。
- 可选任务 ID，用于编辑已有任务。

输出：

- 新建或更新后的 `TaskFlow`。
- 保存草稿后的任务 ID。
- 立即运行后的批次或运行状态。

工作：

- 新建任务编辑器页面。
- 左侧展示模板列表。
- 中间展示参数表单。
- 右侧展示能力需求、运行预览和风险提示。
- 支持保存草稿、立即运行。
- 创建后的任务能回到任务台展示。

边界条件：

- 保存草稿不要求参数全部可运行，但必须保留用户已填内容。
- 立即运行必须通过最小参数校验。
- 能力未配置时允许保存草稿，不允许无提示立即运行。
- 编辑已有任务时不得丢失旧任务的 `steps`、`schedule`、`signin` 等已有字段。

验收：

- 用户能基于京东签到模板创建任务。
- 用户能基于热点监控模板创建任务。
- 用户能修改任务名称和参数。
- 保存后任务台能看到任务。
- 立即运行后进入运行监控。

测试建议：

- 表单校验测试。
- 模板切换测试。
- 保存任务测试。
- 立即运行跳转测试。

### P0-05：运行监控最小闭环

目标：运行过程可观察，失败可处理。

输入：

- 任务 ID。
- 批次 ID。
- 批次列表和详情。
- 介入状态。

输出：

- 批次详情 view model。
- 重试动作。
- 人工介入动作。
- 关联结果入口。

工作：

- 新建运行监控页面。
- 展示任务运行批次列表。
- 展示批次详情：状态、开始时间、结束时间、步骤、日志、错误、截图。
- 支持重试失败批次。
- 支持进入人工介入。
- 支持从任务台失败项和任务编辑器立即运行后跳转进来。

边界条件：

- 批次不存在时显示“批次不存在”并提供返回任务台。
- 批次没有步骤结果时显示批次级状态，不伪造步骤。
- `failed` 可重试；`intervention` 优先显示人工介入；`success` 不显示重试为主操作。
- 重试失败时必须显示错误，不改变原批次状态。
- 人工介入依赖浏览器能力，浏览器不可用时显示能力缺失提示。

验收：

- `running`、`success`、`failed`、`intervention` 状态都有明确展示。
- 失败批次可查看原因。
- `failed` 批次可重试。
- `intervention` 批次可进入浏览器介入。
- 状态值保持现有 `TaskBatchStatus`。

测试建议：

- 批次状态渲染测试。
- 失败详情测试。
- 重试按钮调用测试。
- 人工介入跳转测试。

### P0-06：结果库任务化

目标：结果围绕任务和运行批次组织。

输入：

- 标准结果列表。
- 签到运行历史。
- 热点报告。
- 评论报告。
- 导出任务状态。

输出：

- 统一结果列表 view model。
- 结果详情。
- 导出动作和导出状态。

工作：

- 将 Data Center 主入口重命名为结果库。
- 增加按任务、批次、状态、时间筛选。
- 结果详情展示关联任务和批次。
- 支持 CSV/JSON 导出。
- 展示导出状态、质量状态、空结果状态。

边界条件：

- 标准结果和专项报告可以并存，但必须显示来源类型。
- 专项报告没有批次 ID 时，详情中显示“未绑定批次”，不能生成假 ID。
- 结果内容为空时仍保留结果记录。
- 导出不支持的来源必须禁用导出按钮并说明原因。
- 导出任务失败时保留失败状态和错误信息。

验收：

- 用户能从任务台最近结果进入结果库。
- 用户能从运行监控进入关联结果。
- 结果能追溯到任务和批次。
- 导出成功和失败都有明确状态。

测试建议：

- 结果筛选测试。
- 结果详情测试。
- 导出任务测试。

### P1-01：京东签到模板适配

工作：

## 11. 审查修正记录

本节记录对本计划的设计审查结论，避免后续实施时重新踩同样的问题。

| 问题 | 风险 | 修正 |
| --- | --- | --- |
| 新入口和旧路由关系不清 | 实现时可能删除旧路由，破坏窗口导航、命令面板和历史测试 | 增加路由边界，明确旧路由保留兼容，新菜单只展示新入口 |
| 页面数据来源不清 | 任务台、运行监控、结果库可能各自重复造聚合逻辑 | 增加数据投影边界，第一阶段优先用现有 IPC/API 在渲染层组合 view model |
