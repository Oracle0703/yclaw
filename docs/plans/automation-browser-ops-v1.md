| 模板与录制器 | 已落地最小闭环 | 已支持模板保存/列出/删除、录制开始/停止、步骤预览与导入 |
| 告警中心 | 已落地 | 已支持按 `execution_logs` 聚合告警、已读/未读、批次跳转入口 |
| 验收脚本 | 已落地 | 已新增 Playwright 验收场景，覆盖手动启动、结果导出、介入恢复 |
| Remote Runner | 已落地基础版 | 自动化页已接入远程 Runner 连接、下发、状态、日志与取消能力 |

### 0.2 当前限制

| 项 | 当前说明 |
| --- | --- |
| 任务 CRUD | 当前仍以已有任务资产和最小编辑闭环为主，`task:create/update/delete/detail/clone` 未完整产品化 |
| 调度能力 | 当前 `SchedulerService` 为最小可运行骨架，重启恢复与复杂 cron 策略仍需增强 |
| 录制器 | 当前采用注入脚本 + 页面内缓存的轻量方案，尚未补齐实时流式回传与复杂动作建模 |
| 验证码处理 | 仅支持人工介入后恢复执行，不支持自动破解 |
| E2E 范围 | 当前 Playwright 采用 Vite 页面 + mocked preload 验收，不是完整 Electron 打包态验收 |

## 1. 目标与边界

### 1.1 一期目标

| 项         | 说明                                                   |
| ---------- | ------------------------------------------------------ |
| 产品目标   | 做成一个可日常使用的自动化采集桌面产品                 |
| 核心闭环   | 建任务 → 定时执行 → 查看结果 → 异常介入 → 复跑         |
| 用户角色   | 以数据采集工程师、自动化工程师为主                     |
| 浏览器定位 | 不是独立主产品，而是自动化任务的观察台、调试台、接管台 |

### 1.2 一期不纳入重点

| 方向           | 处理方式                               |
| -------------- | -------------------------------------- |
| 股票分析深化   | 降级为后续扩展，不占一期主资源         |
| 插件生态化运营 | 保留基础能力，不做市场化扩展           |
| AI 自主调度    | 保留助手入口，不作为主链路             |
| 超复杂流程编排 | 不做可视化大编排器，先保证核心采集闭环 |

## 2. 产品策略

### 2.1 推荐路线

| 路线                    | 描述                                                           | 结论         |
| ----------------------- | -------------------------------------------------------------- | ------------ |
| 任务中心 + 浏览器介入台 | 以自动化调度为主，任务异常时允许人工接管当前浏览器会话继续处理 | 一期正式路线 |

### 2.2 核心价值

| 价值     | 说明                                           |
| -------- | ---------------------------------------------- |
| 自动执行 | 任务可以按计划稳定运行，减少重复人工操作       |
| 可观察   | 每次执行都有状态、日志、截图、结果记录         |
| 可介入   | 失败时可以接管页面，完成登录、验证、修正后继续 |
| 可追溯   | 结果、规则、批次、失败原因统一关联             |
| 可复用   | 常见站点可沉淀模板，不需要每次重新配置         |

## 4. 核心用户流程

### 4.1 主流程

| 阶段     | 用户动作                                         | 系统行为                       |
| -------- | ------------------------------------------------ | ------------------------------ |
| 建任务   | 选择目标站点、设置入口页、录制动作、配置提取字段 | 保存任务定义与规则模板         |
| 配调度   | 设置执行周期、重试策略、超时阈值、绑定会话       | 注册调度计划并写入执行队列     |
| 自动运行 | 用户不介入                                       | 调度器触发，执行引擎自动跑任务 |
| 异常处理 | 查看失败任务并接管页面                           | 浏览器介入台恢复到失败现场     |
| 结果处理 | 查看结果、筛选、导出、复跑                       | 关联批次、日志、截图与提取结果 |

### 4.2 失败闭环

| 场景              | 系统响应                          |
| ----------------- | --------------------------------- |
| 页面元素变化      | 标记步骤失败，保存 DOM 快照与截图 |
| 登录态失效        | 暂停任务并提示接管当前会话        |
| 验证码 / 人机校验 | 进入人工介入状态，人工处理后继续  |
| 站点限流          | 延迟重试或终止当前批次            |
| 提取结果异常      | 标记结果为可疑，进入人工复核队列  |

## 5. 实施路线

### 5.1 Phase 1：任务闭环落地（P0）

| 目标               | 关键交付                                                                          |
| ------------------ | --------------------------------------------------------------------------------- |
| 先跑通自动化主链路 | 任务中心（SPEC-A01）、调度器与执行队列（SPEC-A02）、结果入库（SPEC-A05 基础部分） |
| 建立最小可用产品   | 支持创建任务、手动执行、定时执行、查看状态、失败重试                              |

> **注意**：Phase 1 不含规则录制器（SPEC-A04），任务步骤通过手工 JSON 配置。规则录制在 Phase 2 交付。

### 5.2 Phase 2：浏览器介入 + 规则录制（P0）

| 目标             | 关键交付                                                     |
| ---------------- | ------------------------------------------------------------ |
| 让自动化可接管   | 浏览器介入台（SPEC-A03）、失败现场恢复、断点持久化、执行恢复 |
| 降低配置门槛     | 规则录制器 + 提取模板（SPEC-A04），告别手工 JSON             |
| 降低失败处理成本 | 一键打开失败现场并继续当前任务                               |

### 5.3 Phase 3：结果与稳定性增强（P1）

| 目标           | 关键交付                                                                   |
| -------------- | -------------------------------------------------------------------------- |
| 提升日常可用性 | 结果中心完善（SPEC-A05）、批次对比、CSV/JSON 导出、异常筛查、模板复用      |
| 提升稳定性     | 会话管理（SPEC-A06）、告警与日志中心（SPEC-A07）、失败归因、性能与资源优化 |
| 验收闭环       | 按 SPEC-A08 验收 Checklist 逐项通过                                        |

## 6. 里程碑建议

> **前提假设**：1 名开发全职投入，前后端均由同一人承担。如有额外人力，M3/M4 可并行。

| 里程碑                  | 对应 Spec                    | 周期   | 交付内容                                                                |
| ----------------------- | ---------------------------- | ------ | ----------------------------------------------------------------------- |
| M1 基础自动化闭环       | SPEC-A01                     | 2-3 周 | 任务 CRUD、手动执行、DB 表扩建、执行日志、基础结果入库                  |
| M2 调度与复跑           | SPEC-A02                     | 2 周   | 定时任务（node-cron）、并发控制、失败重试、批次状态、重启恢复、复跑入口 |
| M3 浏览器介入台         | SPEC-A03                     | 2-3 周 | 失败接管、断点持久化、当前页面观察、恢复自动执行                        |
| M4 规则录制 + 结果中心  | SPEC-A04, SPEC-A05           | 2-3 周 | 交互式录制器、提取模板 CRUD、结果列表/详情/筛选/CSV 导出                |
| M5 会话 + 告警 + 稳定化 | SPEC-A06, SPEC-A07, SPEC-A08 | 2 周   | 会话管理、登录态持久化、结构化日志、告警聚合、验收 Checklist 逐项通过   |

## 7. 非功能要求

| 维度     | 目标                                           | 度量标准                                                 |
| -------- | ---------------------------------------------- | -------------------------------------------------------- |
| 可用性   | 常见任务配置流程清晰，非开发者也能完成基础配置 | 新用户参照文档 15 分钟内完成首个任务创建与执行           |
| 稳定性   | 长时间运行不因单个任务失败导致整体调度失控     | 3 个并发任务中 1 个 crash 后，其余 2 个正常完成          |
| 可观测性 | 每次执行均可追踪状态、日志、截图、异常原因     | 失败任务 100% 有 error 级日志 + 可关联截图               |
| 可恢复性 | 失败任务能接管、重试、复跑，不需要从头创建     | 人工介入后恢复执行成功率 ≥ 80%（基于可介入场景）         |
| 性能     | 任务执行期间界面可交互，结果查询响应快速       | 1 万条结果分页查询 < 500ms；任务执行期间主进程 CPU < 70% |

## 8. 成功标准

### 8.1 产品级成功指标

| 指标         | 目标                                       |
| ------------ | ------------------------------------------ |
| 任务主链路   | 支持任务创建、调度、暂停、恢复、复跑       |
| 失败介入能力 | 失败任务可恢复到可观察、可接管的页面现场   |
| 结果可追溯性 | 每条结果可关联任务、批次、规则、日志、截图 |
| 模板复用能力 | 常见站点任务可保存为模板并二次复用         |
| 日常可用性   | 用户能把它作为日常采集主工具持续使用       |

### 8.2 验收指标

| 指标           | 目标值                                             | 验证方法                          |
| -------------- | -------------------------------------------------- | --------------------------------- |
| 任务执行成功率 | 对 3 个基准测试站点，连续 7 天采集成功率 ≥ 90%     | 统计 task_batches 中 success 比例 |
| 失败可定位率   | ≥ 90% 的失败批次可从 execution_logs + 截图定位原因 | 随机抽取 20 条失败记录人工复核    |
| 失败可介入率   | 登录失效、验证码、元素变更三类场景均支持人工接管   | 按场景逐一演练                    |
| 结果导出完整度 | 导出 CSV/JSON 与 DB 中数据一致，字段无丢失         | 导出后对比校验                    |
| 进程重启恢复   | 重启后 30s 内定时任务恢复调度                      | kill 进程后重启验证               |
