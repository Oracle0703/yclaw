# YClaw 任务运营主线收敛设计

## 1. 背景判断

| 现象 | 判断 |
| --- | --- |
| 模块很多，但用户不清楚应用主用途 | 当前产品叙事仍像“多工具容器”，缺少压倒性的主流程 |
| Hot / Comment / Signin / Browser / Data Center 各自可用一点 | 能力已经存在，但没有被统一组织成一条用户完成工作的路径 |
| 自动化、Runner、结果、告警、复盘已有数据模型 | 代码基础不差，真正缺的是产品级中心对象和优先级收敛 |
| 继续横向新增模块会加重割裂 | 下一阶段应停止扩张入口，先完成一个端到端运营闭环 |

YClaw 应从“多场景桌面工作台”收敛为：

> 本地优先的 Web 任务运营平台，用于创建、运行、监控、介入、复盘和复用自动化 Web 任务。

## 2. 目标与反目标

| 类型 | 内容 |
| --- | --- |
| 目标 | 将产品主线统一到 `Task -> Run/Batch -> Result -> Alert -> Review -> Template` |
| 目标 | 把 Hot、Comment、Signin 从独立小应用降级为任务类型和任务模板 |
| 目标 | 让首页从模块橱窗变成任务运营总览 |
| 目标 | 第一阶段只打穿一个黄金路径，优先选择热点采集任务 |
| 目标 | 建立后续 Runner 稳定化、数据中心、AI 复盘的上下文基础 |
| 反目标 | 不新增新的业务入口 |
| 反目标 | 不优先建设插件市场、股票深度功能、云多租户或大型流程编排器 |
| 反目标 | 不把 AI 做成泛聊天产品，AI 必须围绕任务上下文工作 |

## 3. 产品定位

| 项目 | 定位 |
| --- | --- |
| 产品一句话 | 本地优先的 Web 任务运营平台 |
| 核心用户 | 小团队运营负责人、任务配置员、执行值班员、数据分析员、自动化工程师 |
| 核心对象 | 任务、运行批次、Runner、日志、结果、告警、复盘、模板 |
| 核心价值 | 把一次性脚本或零散采集能力变成可持续运营、可监控、可复盘、可复用的任务资产 |
| 优先行业场景 | 内容/舆情监控、电商巡检、评论采集、签到巡检、网页数据采集 |

## 4. 核心主线

| 阶段 | 用户动作 | 系统承接 | 现有能力 |
| --- | --- | --- | --- |
| 1. 创建任务 | 选择任务类型并填写目标、规则、频率 | 写入统一 Task 模型 | Automation、Hot、Comment、Signin |
| 2. 执行任务 | 手动执行或定时运行 | 生成 Batch，进入 Runner / Scheduler | BatchService、Runner Scheduler、Remote Runner |
| 3. 观察过程 | 查看队列、状态、日志、截图 | 展示运行时间线和错误原因 | ExecutionLog、Alert、Browser |
| 4. 人工介入 | 登录失效、验证码、页面异常时处理 | 跳转 Browser 现场，恢复或终止运行 | Browser、SessionRegistry |
| 5. 产出结果 | 查看数据、报告、导出、Webhook/API | 结果统一进入 Data Center | ResultService、Data Center |
| 6. 复盘沉淀 | 记录原因、动作、模板修复 | 写入 Review，关联 Template | ReviewService、TemplateService、AI 工具 |

## 5. 信息架构调整

| 当前入口 | 新定位 | 第一阶段动作 |
| --- | --- | --- |
| Workbench 首页 | 任务运营总览 | 替换模块卡片为任务、运行、告警、Runner、结果摘要 |
| Automation | 任务中心 | 保留为主工作区，承接通用任务编辑、执行、批次和复盘 |
| Hot Monitor | 热点采集任务模板 | 不再强调独立入口，优先接入任务创建向导 |
| Comment Monitor | 评论采集任务模板 | 保留能力，后续并入任务类型列表 |
| Signin | 签到巡检任务模板 | 保留能力，后续并入任务类型列表 |
| Browser | 调试与人工介入台 | 从“独立浏览器”改成任务现场、会话和恢复入口 |
| Data Center | 结果与出口中心 | 作为所有任务结果的统一出口 |
| AI Assistant | 任务运营副驾驶 | 围绕任务摘要、失败诊断、复盘草稿、重试建议 |
| Plugin Center | 能力扩展中心 | 降低优先级，作为任务能力扩展而不是主线 |
| Stock | Labs / 示例模块 | 暂停主线投入，避免稀释定位 |

## 6. 首页设计方向

首页应回答“今天要处理什么”，而不是“应用有哪些模块”。

| 区块 | 展示内容 | 操作 |
| --- | --- | --- |
| 今日任务运行 | 运行中、排队中、成功、失败、需介入数量 | 进入任务中心或对应批次 |
| 需处理告警 | P0/P1 告警、超时、Runner 离线、登录失效 | 认领、查看日志、进入现场 |
| Runner 健康 | 本地/远程 Runner 在线、忙碌、离线、容量 | 查看调度面板 |
| 最近结果 | 最新结果、质量问题、导出失败 | 进入 Data Center |
| 快速创建任务 | 热点采集、评论采集、签到巡检、通用采集 | 打开任务创建向导 |
| AI 建议 | 基于失败日志和结果的复盘草稿或重试建议 | 打开 AI 任务上下文 |

## 7. 任务类型收敛

| 任务类型 | 来源模块 | 最小配置 | 产出 |
| --- | --- | --- | --- |
| 热点采集 | Hot Monitor | 平台、关键词、过滤规则、运行频率 | 热点条目、HTML 报告、摘要 |
| 评论采集 | Comment Monitor | 平台、入口、采集限制、外部执行器配置 | 评论结果、AI 回复草稿、报告 |
| 签到巡检 | Signin | 站点、会话、签到策略、通知方式 | 运行记录、奖励信息、失败告警 |
| 通用网页采集 | Automation | URL、步骤、抽取字段、模板 | 结构化结果、截图、日志 |

第一阶段优先实现“热点采集任务”作为黄金路径，因为它依赖较少、结果可见、报告链路已经较完整。

## 8. 黄金路径

| 步骤 | 验收表现 |
| --- | --- |
| 1. 首页点击“创建热点采集任务” | 打开任务创建向导，默认选择热点采集类型 |
| 2. 填写平台、关键词、过滤和频率 | 保存为统一 Task，并保留 hot source 专项配置 |
| 3. 点击立即运行 | 创建 Batch，状态进入运行中 |
| 4. 查看运行详情 | 能看到步骤日志、状态、错误和批次信息 |
| 5. 运行完成 | Result / Hot Report 可从任务详情和 Data Center 进入 |
| 6. 失败场景 | 产生 Alert，可在首页看到并进入处理 |
| 7. 复盘 | 能基于 Batch 创建 Review，并关联后续动作 |

## 9. 数据与边界原则

| 原则 | 说明 |
| --- | --- |
| Task 是中心对象 | 任何可运行能力都必须能映射到 Task |
| Batch 是一次运行 | 所有执行结果、日志、告警、报告必须能追溯到 Batch |
| Result 是统一出口 | 专项报告可以存在，但结构化结果必须进入 Data Center |
| Alert 是处理入口 | 失败、超时、登录失效、Runner 离线都应形成可处理告警 |
| Review 是闭环终点 | 失败不是终点，必须能沉淀原因、处置和模板改进 |
| 模块是工作区，不是孤岛 | 每个模块都要说明它服务主线中的哪个阶段 |

## 10. 阶段计划

| 阶段 | 时间 | 目标 | 产出 |
| --- | --- | --- | --- |
| Phase 0 | 1 周 | 产品收敛与信息架构落地 | 首页、导航、文案、模块优先级调整 |
| Phase 1 | 2 周 | 热点采集黄金路径 | 创建、运行、结果、报告、告警、复盘闭环 |
| Phase 2 | 2 周 | Runner 稳定化 P0 | 心跳、超时、lease 回收、orphan 修复、状态解释 |
| Phase 3 | 1-2 周 | Data Center 联动 | 从任务/批次跳转结果、质量问题、导出 |
| Phase 4 | 1-2 周 | Browser 介入闭环 | 失败现场跳转、会话恢复、处理记录 |
| Phase 5 | 1 周 | AI 复盘助手 | 失败摘要、重试建议、复盘草稿 |

## 11. 暂停与降级清单

| 项目 | 处理 |
| --- | --- |
| 股票分析深度增强 | 暂停主线投入，标记为 Labs |
| 插件市场 | 暂停，只保留本地插件生命周期 |
| 新增业务入口 | 暂停 |
| 泛 AI 聊天体验 | 暂停，AI 只围绕任务上下文增强 |
| 大型可视化流程编排 | 暂停，先保证任务闭环 |
| 云同步 / 多租户 | 暂停，保持本地优先 |

## 12. 成功标准

| 指标 | 标准 |
| --- | --- |
| 新用户理解 | 打开首页 30 秒内能理解“这是任务运营平台” |
| 黄金路径完成 | 一个热点采集任务能从创建到运行、结果、告警和复盘走通 |
| 模块关联 | 首页、任务中心、Browser、Data Center、AI 都能围绕同一 Task / Batch 跳转 |
| 功能收敛 | 主要导航不再鼓励用户随机进入互不相关的模块 |
| 工程边界 | 新增功能必须声明映射到 Task 主线的哪个阶段 |

## 13. 后续实施原则

| 原则 | 说明 |
| --- | --- |
| 先主线，后增强 | 没有进入 Task 主线的功能不进入 P0/P1 |
| 先一个黄金路径，后多个任务类型 | 先做好热点采集，再推广到评论和签到 |
| 先可解释，后智能化 | AI 之前先保证日志、状态、错误原因稳定 |
| 先本地可用，后生态扩展 | 插件市场和云协作等主线稳定后再启动 |
| 先真实数据，后视觉 polish | 首页必须优先接真实任务、批次、告警、Runner 数据 |
