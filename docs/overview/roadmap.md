## 1. 项目定位再确认

| 维度 | 结论 |
| --- | --- |
| 产品本质 | YClaw 是一个模块化、插件化、可自动化的桌面工作台容器；在当前阶段，产品主线进一步收敛为“小团队任务运营中台”。 |
| 核心人群 | 运营负责人、任务配置员、执行值班员、数据分析员，以及自动化 / 插件高级用户。 |
| 当前主线 | 以“任务运营闭环产品化”为近期最优主线，把任务、批次、Runner、调度、结果、日志、告警、AI 辅助串成闭环。 |
| 长期形态 | 桌面端综合生产力平台：任务运营中台 + 自动化/RPA + 数据分析 + AI 助理 + 插件生态 + 模板市场。 |

## 3. 后续拓展总逻辑

YClaw 后续不宜按“功能清单”横向扩张，而应按“任务运营闭环”纵向打穿。

| 层级 | 目标问题 | 关键能力 | 成功标志 |
| --- | --- | --- | --- |
| L1 可运行 | 用户能不能完成一次任务？ | 任务创建、手动执行、基础步骤运行、状态反馈。 | 一个任务可以从创建到执行完成。 |
| L2 可调度 | 用户能不能把任务交给系统稳定跑？ | 调度器、执行队列、并发控制、超时、失败重试、lease 恢复。 | 任务能按计划稳定触发并记录批次，并在 Runner 波动时保持可恢复。 |
| L3 可协作 | 团队能不能围绕任务分工和交接？ | 工作区、负责人、值班、审核、认领、交接留痕。 | 异常任务有人跟进，任务变更有责任归属。 |
| L4 可观察 | 团队能不能知道发生了什么？ | 结果中心、结构化日志、截图、执行步骤时间线、告警聚合。 | 每次执行可查、可筛选、可导出、可定位失败。 |
| L5 可介入 | 失败时团队能不能接管？ | 浏览器介入台、断点恢复、登录态绑定、人工恢复执行。 | 登录失效、验证码、元素变更等场景可人工处理后继续。 |
| L6 可复用 | 团队能不能降低重复配置成本？ | 规则录制、提取模板、模板复制、多站点模板库、复盘沉淀。 | 常见任务可通过模板快速创建。 |
| L7 可智能 | 系统能不能辅助判断和优化？ | AI 失败诊断、规则草稿、重试策略、任务问答、复盘初稿。 | AI 能基于任务、日志、结果给出可执行建议。 |
| L8 可生态 | 能不能沉淀第三方能力？ | 插件化采集、站点适配器、插件市场、社区模板。 | 外部插件/模板能安全安装、运行和复用。 |

## 4. 推荐产品路线

### 4.1 近期主路线：小团队任务运营闭环

| 阶段 | 目标 | 覆盖模块 | 交付结果 |
| --- | --- | --- | --- |
| Phase 0 | 实现缺口整改 | App 装配、IPC、AI、任务、股票、插件、浏览器、窗口/托盘。 | 文档标记与真实实现对齐，核心通道不再是 UI 壳。 |
| Phase 1 | 任务与调度底座（已进入可用版） | 任务中心、批次、调度器、执行队列、本地/远程 Runner 池。 | 任务可创建、启动、暂停、恢复、复跑，并支持统一 Runner 调度。 |
| Phase 2 | 协作与值班机制（已落地基础版） | 工作区、负责人、审核、告警认领、交接留痕。 | 工作区、版本审核、告警认领/转交/备注/升级/关闭与动作历史回看已接入，并补上当前/下一班解析、轻量班次安排面板、升级负责人解析与超时自动升级；完整日历视图仍可后续增强。 |
| Phase 3 | 结果与日志闭环（已落地基础版） | 结果中心、结构化日志、导出、错误聚合。 | 已支持质量状态、证据链、版本追溯、跨批次质量分析、必填字段校验与最小批次数量校验。 |
| Phase 4 | 浏览器介入闭环 | 浏览器介入台、断点恢复、会话绑定、远程运行时恢复。 | 失败现场可观察、可接管、可恢复自动执行。 |
| Phase 5 | 录制、模板与复盘（已落地基础版） | 规则录制器、提取模板、模板复制、复盘记录。 | 复盘记录、模板关联、回流建议、可执行回流草稿、草稿应用、选择器字段自动改写、模板版本/废弃/说明/插件依赖治理与后续动作已接入，更复杂字段映射仍待补齐。 |
| Phase 6 | AI 运营副驾驶（已落地基础版） | 任务状态问答、失败解释、规则草稿、重试建议、复盘初稿。 | 已具备任务摘要、告警摘要、Runner 状态、复盘初稿工具，后续再做主动建议。 |
| Phase 7 | 插件化与生态 | 站点适配器、结果处理器、采集插件、模板市场。 | 采集能力可扩展、可分发、可复用。 |

### 4.2 暂不作为近期主路线的方向

| 方向 | 暂缓原因 | 适合启动条件 |
| --- | --- | --- |
| 股票分析深度增强 | 当前自动化主链路更能体现产品核心价值。 | 自动化 M5 验收通过，结果/调度/日志稳定。 |
| 插件市场生态 | 需要分发、安全、审核、后端服务和冷启动内容。 | 插件生命周期、本地安装、权限隔离先闭环。 |
| 云同步与多租户协作 | 涉及账号、权限、云端后端、同步冲突处理。 | 本地小团队协作闭环稳定且有明确跨团队需求。 |
| 大型可视化流程编排 | 复杂度高，容易拖慢核心采集闭环。 | 规则录制和任务模板已经成熟，用户明确需要复杂流程。 |
| AI 主动智能 | 依赖日志、任务、结果、事件流等上下文质量。 | AI 工具调用和任务/日志上下文先稳定。 |

## 5. 模块拓展矩阵

| 模块 | 当前角色 | 下一步重点 | 后续演进 |
| --- | --- | --- | --- |
| App Shell | 应用容器与窗口生命周期基础。 | 核实多窗口/单窗口模型、托盘行为、关闭策略。 | 多实例窗口、模块弹出、多显示器工作流。 |
| IPC / EventBus | 模块间通信地基。 | 补齐缺失 handler，统一错误格式，避免渲染进程永久等待。 | 类型化通道治理、审计、限流、事件回放。 |
| 自动化引擎 | 核心业务引擎。 | 打通任务执行、步骤日志、失败断点、批次状态。 | 条件分支、循环、复杂 RPA 工作流。 |
| 任务中心 | 中台的任务资产入口。 | 任务版本、审核、负责人、模板关联、版本对比。 | 任务依赖、批量操作、更细粒度字段对比。 |
| 执行 / 告警 / 结果中心 | 中台的日常运营入口。 | 队列、批次、告警、结果、证据链联动。 | 异常检测、数据质量评分、趋势报表。 |
| 浏览器模块 | 自动化观察台、调试台、接管台。 | 明确真实 `WebContentsView` 接入或短期降级为会话控制台。 | 会话分组、多账号隔离、标签拖拽、站点调试工具。 |
| AI 助手 | 平台智能交互层。 | 先做任务状态、系统状态、失败诊断、导航等低风险工具。 | 操作预览、撤销、主动晨报、调度优化、规则生成。 |
| 插件系统 | 长期生态扩展层。 | 先闭环本地插件扫描、安装、启停、卸载、权限确认。 | 插件沙箱、资源限制、市场、签名、评分。 |
| 股票分析 | 数据分析场景入口。 | 保持基础 K 线和指标能力，避免抢主线资源。 | 策略回测、自定义指标、采集数据联动分析。 |
| 总控页面 | 工作台驾驶舱。 | 展示任务、结果、异常、系统健康和快捷入口。 | 可拖拽布局、小组件、团队看板、模板推荐。 |

## 6. 优先级建议

| 优先级 | 工作项 | 原因 | 不做的代价 |
| --- | --- | --- | --- |
| P0 | 调度恢复与超时/重试收口 | 统一 Runner 池已经可用，下一步是保证任务能长期稳定跑。 | 现有调度只能演示，不适合持续运行。 |
| P0 | 协作基础与责任归属 | 任务和异常已进入可运营阶段，但责任人、认领、交接规则仍薄弱。 | 团队使用时容易出现无人跟进和上下文丢失。 |
| P0 | 结果、日志、队列联动补齐 | 调度面已经出现，但失败定位仍依赖跨面板手工拼接。 | 出问题时仍然难复盘，无法支撑真实运维。 |
| P0 | 远程 Runner daemon 稳定化 | 远程执行已可联调，需要补会话、结果、持久化和长连健壮性。 | 远程能力停留在 demo，无法承担生产任务。 |
| P1 | 浏览器介入与恢复闭环 | runner 失联、登录态失效后的人工接管仍是关键缺口。 | 失败任务需要完全重来，使用成本高。 |
| P1 | 规则录制、模板与复盘 | 降低任务配置门槛，并让经验可以沉淀。 | 产品仍偏开发者工具，普通用户难上手，组织经验难积累。 |
| P1 | AI 失败诊断与调度建议 | 在已有日志、Runner 状态和结果基础上增效。 | AI 仍然难以深入任务运营主线。 |
| P2 | 插件化采集能力 | 支持站点适配器和结果处理扩展。 | 长期扩展受限，但不影响一期闭环。 |

## 8. 验收指标

| 指标 | 建议目标 | 验证方式 |
| --- | --- | --- |
| 任务执行成功率 | 3 个基准站点连续 7 天成功率 ≥ 90%。 | 统计批次成功率。 |
| 告警认领及时率 | 严重告警 10 分钟内认领率 ≥ 95%。 | 统计告警处理时延。 |
| 失败可定位率 | ≥ 90% 失败批次可通过日志 + 截图定位原因。 | 抽样人工复核。 |
| 失败可介入率 | 登录失效、验证码、元素变化三类场景均可接管。 | 场景演练。 |
| 结果可追溯性 | 每条结果可关联任务、批次、规则、日志、截图。 | 数据链路检查。 |
| 重启恢复 | 应用重启后 30 秒内恢复调度。 | kill 进程后重启验证。 |
| 查询性能 | 1 万条结果分页查询 < 500ms。 | 本地压测。 |
| 用户上手 | 新用户 15 分钟内完成首个任务创建和执行。 | 可用性测试。 |

## 9. 决策建议

| 决策点 | 推荐结论 |
| --- | --- |
| 产品主线 | 选择“小团队任务运营闭环”，以自动化采集为主业务载体。 |
| 浏览器模块 | 如果目标是兑现原始 SPEC，优先真实接入 `WebContentsView`；如果目标是快速交付，短期降级为“浏览器会话控制台”并同步文档。 |
| AI 助手 | 不做泛聊天优先，先做任务助理、失败诊断、规则草稿、复盘初稿和状态问答。 |
| 插件系统 | 先闭环本地生命周期和权限确认，再考虑插件市场。 |
| 股票分析 | 保持基础能力，待自动化采集稳定后再回归策略回测和指标扩展。 |

| 5 | 决定浏览器介入台与远程恢复的交互路线。 | 真实接管能力或明确降级范围。 |
| 6 | 在稳定日志和 Runner 状态基础上接入 AI 任务助理。 | 失败诊断、重试建议和调度解释能力。 |

## 11. 总结

YClaw 最合理的拓展路径是：

> 先做稳“任务调度与结果闭环”，再补强“协作值班与浏览器介入”，随后用“AI 助手”和“插件系统”提高效率与扩展性，最后再进入模板市场、跨团队协作和生态化阶段。

近期不建议同时发散到股票深度分析、插件市场、云多租户同步和大型流程编排。它们都是合理方向，但应排在小团队任务运营主链路稳定之后。
