## 1. 产品背景与目标

现代桌面工作需要同时使用多种工具：股票分析、网页自动化、采集脚本、浏览器、多插件能力等。这些工具分散在不同软件中，不利于统一管理与工作流程整合。

本应用旨在打造一个可扩展、模块化、插件驱动的跨平台桌面工作台容器，使用户能在一个应用内高效完成多类复杂任务。

## 2. 产品定位

- 容器级桌面应用（Containerized Desktop Platform）
- 基于 Electron + React + Vite
- 支持多业务入口、多场景、多插件扩展
- 提供自动化、采集、分析、浏览等核心能力
- 可最终演进为一款桌面端的综合生产力平台

### 2.1 小团队任务运营中台主线

在当前阶段，YClaw 不再只被定义为“多工具聚合容器”，而是进一步收敛为：

> 一个面向 3~20 人小团队的桌面端任务运营中台，用于统一编排、执行、监控、告警、复盘和复用自动化任务。

主线价值聚焦如下：

| 维度 | 定位说明 |
| --- | --- |
| 核心对象 | 任务、批次、执行实例、Runner、告警、结果、模板、复盘记录 |
| 核心目标 | 让任务从一次性脚本升级为可持续运营的业务资产 |
| 目标用户 | 任务配置员、执行值班员、运营负责人、数据分析员、插件管理员 |
| 协作方式 | 本地为主，支持小团队共享任务资产与执行状态，不以多租户云平台为前提 |
| 近期产品主线 | 自动化采集产品化 → 小团队任务运营闭环 → 运营副驾驶与能力生态 |

专项需求扩展详见 `docs/product/task-operations-center.md`。

## 3. 用户角色与典型场景

### 3.1 用户角色

| 用户类型 | 需求点 |
| --- | --- |
| 运营负责人 | 关注任务 SLA、告警、团队效率、资源利用率 |
| 任务配置员 | 负责任务编排、模板维护、发布审核和流程调试 |
| 执行值班员 | 负责执行监控、异常介入、交接和恢复 |
| 数据分析员 | 关注结果产出、质量趋势、导出与复盘 |
| 数据采集 / 自动化工程师 | 关注自动化浏览器、采集策略、任务调度和复杂页面适配 |
| 量化研究员 | 关注行情数据、指标分析、策略验证 |
| 高级用户 / 开发者 | 关注插件拓展、自定义工具、能力集成 |

### 3.2 典型使用场景

#### 场景 A：数据采集工程师，电商价格监控

用户在「自动化采集」模块中创建任务流：打开目标电商页面 → 定位商品价格元素 → 提取数据 → 存入本地 SQLite → 设置每日定时执行。任务执行过程中可在「内嵌浏览器」中实时观察页面操作，异常时自动重试并记录日志。

#### 场景 B：量化研究员，技术指标分析

用户进入「股票分析」模块，接入行情数据源（WebSocket 实时推送），查看 K 线图并叠加 MA、MACD、RSI 指标。编写 JS 策略脚本，对历史数据进行快速验证，导出分析结果。

#### 场景 C：自动化工程师，网页表单批量填写

用户在「自动化采集」模块中录制表单操作流程（点击、输入、下拉选择），保存为任务模板。批量导入 CSV 数据，自动化引擎逐条执行填写任务，失败项标记后支持断点重试。

#### 场景 D：高级用户，插件开发与集成

开发者按照插件 API 规范开发 OCR 插件，声明所需权限（文件系统读取 + 网络访问），打包后通过「插件中心」安装。V1.0 中插件 UI 统一运行在受控的 `plugin-host` 宿主页内，仅允许受信来源插件接入；其他模块通过 IPC 调用 OCR 能力。

#### 场景 E：值班执行员，异常告警处理与任务恢复

执行值班员在「执行中心」看到某个电商采集任务因登录态失效进入“需人工介入”状态。系统已自动附带失败步骤、截图、最近日志和推荐处理动作。值班员进入「浏览器介入台」完成重新登录后，任务从断点继续执行，随后在「结果中心」确认本次批次的结果完整性并关闭告警。

#### 场景 F：运营负责人，任务复盘与模板沉淀

运营负责人在「工作台总览」中发现某类站点任务近 7 天失败率升高，进入「告警中心」查看异常聚类后，要求任务配置员更新模板。配置员将本次修复沉淀为模板新版本，后续同类任务创建时直接复用，减少重复排查成本。

## 4. 整体功能架构

```text
+----------------------------------------------------------+
|                    Desktop Application                   |
|                  (Electron App Shell)                    |
+----------------------------------------------------------+
| Multi-entry Workspace | Task Operations Center | Plugin  |
+----------------------------------------------------------+
|          Module Communication Bus (IPC + Event)          |
+----------------------------------------------------------+
| Analytics Engine | Automation Engine | WebView | AI Assistant |
+----------------------------------------------------------+
|                System Services & Infrastructure          |
|  Logging | Permission | Storage | Config | Update | DB   |
+----------------------------------------------------------+
```

### 模块通信机制说明

- 主进程 ↔ 渲染进程：Electron IPC（contextBridge 安全暴露）
- 模块间事件分发：统一走主进程 EventBus + IPC fan-out，不依赖 BroadcastChannel
- 模块内状态共享：基于 Zustand + 持久化中间件
- 插件 → 宿主：通过 Plugin API Bridge（受限 IPC 通道，权限校验后转发）
- 事件总线：主进程维护全局 EventEmitter，各模块通过 IPC 订阅/发布事件

## 5. 详细模块说明

### 5.1 应用壳（App Shell）

- Electron 主进程（要求 Electron ≥ 28）
- 窗口管理、多窗口支持
- WebContentsView 容器管理
  - BrowserView 已在 Electron 28+ 废弃，统一使用 WebContentsView
- IPC 通信（基于 contextBridge 安全暴露 API）
- 系统菜单、托盘、更新器

### 5.2 多入口模块系统（Multi-entry Module System）

为每个业务场景创建独立入口，包括：

- 独立路由
- 独立状态管理
- 分离构建产物
- 可热加载 / 可禁用

技术实现方案：

- V1.0：基于 Vite 多入口（MPA 模式）构建，每个模块为独立 HTML 入口，通过动态 `import()` 实现模块懒加载
- V2.0：评估引入 Module Federation 实现跨应用模块共享与独立部署

示例模块：

- 股票分析
- 网页自动采集
- 内嵌浏览器
- 插件中心
- 自定义工具（Terminal、Markdown 编辑器等）

### 5.3 插件系统（Plugin Engine）

核心职能：

- 插件安装、卸载、启用、禁用
- 插件运行模型
  - V1.0：共享 `plugin-host` 宿主页 + 受限 preload
  - V1.5：升级为按插件独立进程
- 插件权限声明（例如：网络、文件系统、自动化权限）
- 插件 UI 加载
  - V1.0 统一通过 `plugin-host`
  - 不引入 `iframe`
- 插件 API（通过主进程 IPC 提供）

插件权限分级模型：

- Level 1（UI 只读）：仅允许渲染 UI、读取公开应用状态，无需用户授权
- Level 2（网络 + 存储）：允许网络请求、读写插件专属存储空间，安装时需用户确认
- Level 3（自动化 + 文件系统）：允许调用自动化引擎、访问用户文件系统、操作 WebContentsView，每次使用需用户显式授权

阶段规划：

- V1.0：实现基础权限声明 + 受信来源策略（官方 / 本地开发 / 手动允许列表）
- V1.5：升级为按插件进程级隔离 + 资源限制

可支持插件示例：

- OpenClaw 自动化能力
- OCR 模块
- PDF 处理器
- 爬虫脚本插件
- AI 推理插件（本地模型）

### 5.4 自动化与采集引擎（Automation Engine）

提供类似浏览器 RPA 的能力：

- DOM 查询
- 点击 / 输入 / 滚动行为模拟
- 页面内容采集
- 截图、选择器生成
- 任务流（Flow → Step → Action）
- 错误重试、断点继续

### 5.5 数据分析引擎（Analytics Engine）

用于金融或行情类分析：

- 行情数据源接入（REST / WebSocket）
- 技术指标库（MA、MACD、RSI、BOLL 等）
- 图表绘制（K 线、分时、指标叠加）
- 策略脚本执行（JS / Python）
  - JS 策略：在 Worker 线程或沙箱 VM 中执行
  - Python 策略：V1.0 通过 `child_process.spawn()` 调用本地 Python 环境执行脚本，通过 stdin/stdout JSON 协议通信；V2.0 评估 Pyodide（WASM）方案实现无依赖 Python 运行时
- 回测框架（未来扩展）

### 5.6 内嵌浏览器（Embedded Web Workspace）

- 多标签页
- 按工作区或配置文件的会话隔离（Cookie / LocalStorage）
- 受控脚本执行（仅自动化引擎内部生成或审核通过的脚本模板）
- 可被自动化引擎控制（通过 WebContentsView.webContents API）
- 支持任务化自动浏览

### 5.7 配置中心

- 全局配置
- 模块配置
- 插件配置
- 自动化任务配置
- 配置文件可备份 / 导出

### 5.8 日志中心

- 应用运行日志
- 自动化任务日志
- 插件日志
- 错误分析
- 导出调试包

### 5.9 权限与安全模块

- 插件权限沙箱（三级权限模型，详见 5.3）
- 文件读取白名单
- WebContentsView 注入安全控制（受控脚本模板、导航白名单、preload 暴露面最小化）
- IPC 消息安全校验（schema 校验 + 频率限制）
- 应用密钥管理

### 5.10 数据存储模块（Data Storage）

数据持久化方案：

- 结构化数据（任务配置、股票数据、插件元信息、用户设置）：SQLite（通过 better-sqlite3 同步访问）
- 大文件 / 二进制（采集截图、导出文件、日志归档）：应用数据目录文件系统存储
- 临时缓存 / 渲染进程数据：IndexedDB（浏览器原生）
- 配置文件：JSON / YAML 文件（便于备份导出）

数据目录结构：

- `{userData}/databases/`：SQLite 数据库文件
- `{userData}/storage/`：大文件存储
- `{userData}/config/`：配置文件
- `{userData}/logs/`：日志文件
- `{userData}/plugins/`：插件安装目录

### 5.11 AI 运营助手（AI Assistant）

提供智能化运营辅助能力：

- **AI 服务层**（主进程）：
  - `AIService`：LLM 调度核心，管理对话上下文、工具调用、多轮对话
  - `ContextManager`：上下文收集器，获取系统指标、模块状态、任务列表等实时信息
  - `ToolRegistry`：AI 工具注册与执行，支持 function calling
  - `LLMProvider`：Provider 抽象层，支持 OpenAI API 和 Ollama 本地模型

- **内置 AI 工具**：
  - `task_list`：查询自动化任务列表、任务状态
  - `system_status`：获取系统资源状态（CPU / 内存 / 窗口数）
  - `navigate`：模块导航，快速跳转到指定功能页面

- **渲染端 UI**：
  - AIChatPanel（Ctrl+J）：悬浮气泡 + 展开面板，支持多轮对话
  - Zustand 状态管理（对话历史、加载态、面板展开状态）
  - 通过 IPC `ai:chat` 通道与主进程 AI 服务通信

阶段规划：

- V1.1（已实现）：基础 AI 服务层 + 对话面板 + 3 个内置工具
- V2.0：Streaming 响应、更多工具集成、多模型切换、对话历史持久化

### 5.12 任务运营中台（Task Operations Center）

该模块是当前产品主线的业务组织层，用于将自动化、Runner、日志、结果、AI 和插件能力编排为一条完整的团队运营闭环。

核心职责：

- 工作区与成员协作
- 任务版本、审核与发布
- 执行中心（批次、实例、队列、Runner 调度）
- 告警中心（认领、升级、恢复、关闭）
- 结果中心（结果聚合、质量校验、证据链、导出）
- 模板与复盘资产沉淀

关键业务对象：

- Workspace：团队协作边界与默认配置容器
- Task / TaskRevision：任务与其发布版本
- Batch / Execution：执行批次与执行实例
- Runner：本地/远程执行资源
- Alert：异常告警与处理记录
- ResultSet：结构化结果集合
- Template / Review：模板资产与复盘记录

状态管理要求：

- 任务状态支持草稿、待审核、已发布、排队中、执行中、需人工介入、成功、失败、已复盘、已归档
- 告警状态支持新告警、已指派、处理中、已升级、已恢复、已关闭
- 高风险任务与高权限插件组合在发布前需额外提示或审核

产品目标：

- 让任务从一次性执行脚本升级为可持续运营的团队资产
- 让异常从“失败即结束”升级为“告警 → 介入 → 恢复 → 复盘”的可运营闭环
- 让结果从“只看日志”升级为“结构化结果 + 证据链 + 复盘沉淀”

## 9. 非功能性需求

### 性能

- 启动时间 < 2s（冷启动到主界面可交互）
- 模块动态加载（单模块加载时间 < 1s）
- 插件宿主隔离不影响主界面性能（主进程 CPU 占用 < 5%）
- 内存占用 < 500MB（基础模块全部加载状态）
- 单插件加载时间 < 500ms
- 并发自动化任务支持 ≥ 5 个
- SQLite 查询响应 < 50ms（常规查询）

### 安全性

- 插件权限声明机制（三级权限模型）
- 文件系统访问限制（白名单 + 沙箱目录隔离）
- IPC 通信校验（schema 校验 + 频率限制）
- WebContentsView 脚本注入限制（受控脚本模板 + 导航控制）

### 可扩展性

- 模块化结构（Vite 多入口独立构建）
- 插件可独立分发（标准 `.ycplugin` 包格式）
- 插件市场（未来）
